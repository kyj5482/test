# 매일 100만 대에서 수집하는데 왜 하루 1대도 분석 못할까?

`관심사: 데이터` · `퍼즐 4조각`

북미의 빅데이터센터: 물리 서버 100여 대, 실제 활용은 10대 이하 — 대부분 스토리지.
매일 100만 대의 차량에서 데이터를 수집하지만 분석은 하루 1대도 안 되는 미스매치.
게다가 수집 비용만 연 $2M 이상. 이 퍼즐은 "Vehicle Twin"이라는 그림으로 맞춰졌다.

## 🧩 조각 1 — 수집과 활용의 미스매치부터 끊는다

차량 판매가 늘고 데이터 보존 정책이 1년→3년으로 바뀌면, 이 비용은 더 커질 운명이었다.
그래서 **실제 안전 분석에 필요한 필수 데이터를 정의하고 수집을 축소**했다.
담당자들과 수많은 논쟁이 있었지만, "나중에 필요하면 추가 수집"이 "혹시 몰라 전부 수집"보다 싸고 빠르다는 것을 어필했다.
동시에 이메일로 요청받아 수동 파싱해주던 데이터 제공을 **API로 24/7 자동화**해 반대하던 사람들도 만족시켰다.

## 🧩 조각 2 — 설계 중심에서 목적성 데이터 마트로

과거에는 리소스가 부족해 공통화·표준화 마트 "설계"에 집중했다면,
스토리지가 싸진 지금은 **마스터 데이터만 잘 잡고, 서비스/의사결정 포인트별로 목적성 마트**를 만든다.
법인이 원하는 Feature를 선정하면 기본 통계(Min, Max, P10/P50/P90)를 일/월 단위 Summary로 제공 — Ondemand 분석이 상시 모니터링으로 바뀌었다.

## 🧩 조각 3 — 유스케이스로 증명한다: 12V 배터리

고객 불만 최상위권인 12V 품질 이슈:

- 상시 모니터링으로 **암전류 발생 즉시 판단**
- 비즈니스 데이터(수리 이력)와 결합 → S/W 업그레이드 수리를 받았는데도 재현되면 **수리 방법 자체의 문제**를 알려줌

플랫폼의 가치는 아키텍처 다이어그램이 아니라 이런 유스케이스 하나가 증명한다.

## 🧩 조각 4 — 이름의 정치학

이 플랫폼의 원래 이름은 Vehicle Twin이었다. "디지털 트윈"이라는 큰 이름 때문에 사방에서 공격받았고, 결국 **Vehicle Data Stream**으로 이름을 바꾸고 나서야 조용히 발전할 수 있었다.
차량-서버 스펙은 향후 업데이트 없이도 수집 정책을 바꿀 수 있게 설계했다 — 과거에는 수정 하나에 차량 개발 프로세스상 3년이 걸렸기 때문이다.
**야심은 설계에 넣고, 이름은 겸손하게.**
