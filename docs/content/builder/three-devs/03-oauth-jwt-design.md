# 글로벌 차량 API 인증은 어떻게 설계할까?

`관심사: 플랫폼` · `퍼즐 3조각`

계정에는 OAuth, 파트너사별 고객 데이터·차량 기능 인가에는 JWT.
현대·기아·제네시스 커넥티드카 플랫폼의 인증 설계에서 남은 원칙들.

## 🧩 조각 1 — 인증(누구냐)과 인가(뭘 할 수 있냐)를 분리한다

가장 흔한 설계 실수는 이 둘을 한 덩어리로 만드는 것이다.
- **OAuth**: 사용자가 누구인지 — 계정 시스템이 책임진다
- **JWT**: 이 파트너가 이 고객의 어떤 데이터·어떤 차량 기능까지 쓸 수 있는지 — 토큰 안의 클레임이 책임진다

분리해두면 파트너가 늘어나도 계정 시스템은 건드리지 않는다. 3개 브랜드 × 여러 파트너 조합이 이 구조 덕에 곱셈이 아니라 덧셈이 됐다.

## 🧩 조각 2 — 차 문을 여는 API는 웹 API와 다르다

차량 제어 API의 오남용은 서비스 장애가 아니라 물리적 사고다.
그래서 토큰의 수명은 짧게, 권한은 기능 단위로 잘게(원격 시동과 도어 잠금 해제는 다른 권한),
그리고 모든 제어 호출은 감사 로그로. 해커들의 API 공격 소식이 들릴 때마다 심장이 멎는 듯했던 경험이 설계 기준을 만들었다:
**"이 토큰이 유출되면 최악이 뭔가?"**를 먼저 쓰고 시작하는 것.

## 🧩 조각 3 — 게이트웨이에서 끝낼 것은 게이트웨이에서 끝낸다

토큰 검증·유효기간·권한 매칭은 API 게이트웨이(tyk) 레이어에서 처리하고, 서비스 코드에는 비즈니스 로직만 남겼다.
인증 로직이 서비스마다 복붙되는 순간, 보안 패치는 서비스 수만큼의 배포가 된다.
3명이 운영하는 팀에게 이것은 취향이 아니라 생존 조건이었다.
